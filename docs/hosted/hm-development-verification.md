# Host-mediated 开发验证顺序

本页保留实施期间的检查顺序与历次观测。component-v2 MVP 已交付，当前入口为
[发布记录](../releases/hm-mvp-component-v2-freeze-marker.md)和[故障恢复](hm-mvp-recovery.md)。
以下检查不构成发布后的待办清单；后续工作应按实际影响范围复用原证明，避免非必要测试和重流程。
后续任务执行[现行实施约定](../guides/implementation-discipline.md)，不照搬下文历史整轮顺序。

局部诊断不授予资格；正式 HM-MVP 仍绑定精确
提交、部署 profile、冻结业务输入和完整原始证据，经完整机械核验及 HM-09 接受。

## 先查前置条件

在启动耗时矩阵或真实模型交接前，检查：

1. 部署安装与 provenance、服务身份和权限 probe、输入投影，均绑定明确 C/B/D。
2. 固定 snapshot、Qlib view、data-qualified release 位于各自预期路径；复制使用
   新目的地，拒绝符号链接，逐项验证绑定。不能把 artifacts 再复制进已有 artifacts。
3. 完整 source index 的实际字节数、记录数和适用上限；已有科研 authority 可以用于
   估计剩余完整布局，但估计必须标为诊断，不能构造未来来源证据或替代原始文件。
4. 已完成场景的各来源谓词。局部检查保留原始故障、恢复、退出与来源绑定，说明哪些
   分母尚未核验；未经完整来源检查的结论不能写入正式资格报告。

每项记录输入身份、实际耗时、文件数或读取字节数，以及结果与限制。发现失败立即
保留原件，针对失败环节修正并重验，不用另一轮完整矩阵代替最小复现。

前置工具见 [hosted_early_checks.py](../../scripts/hosted_early_checks.py)。四个模式是
`deployment`、`capacity`、`gate --case-id Qxx` 和
`original-case --case-id Qxx --scenario <冻结场景>`。所有模式要求明确
`--manager-root`、`--commit`、`--profile-hash`、`--business-inputs-hash` 和
新独立 `--output`。`gate` 还要求已有 `--bundle`；`capacity` 要求已有 `--index`。
局部门检查只绑定该门的来源闭包，报告未检查的完整分母，保持 NOT_QUALIFIED；
失败尚未导出的场景使用 `original-case` 读取有限的原始退出和 failure 结构。

使用 `python -B` 启动诊断，禁用 Git 可选写锁。`git status` 会在可写工作树刷新
`.git/index`，不能仅因命令名是 status 就视为不会写入。工具核对检查前后原件状态，
任何变动都失败并保留原件。第 32 轮的初版部署诊断缺少这一保护，随后 provenance
硬核验拒绝；该失败与原始诊断均保留，不能删除或重置 index 来修复旧验收根。

## 开发时局部验证

修正代码后先运行受影响组件的测试、类型与静态检查。部署、输入布局和证据容量问题
优先使用独立的新诊断输出目录；不覆盖原资格根、失败根或已接受工件。

不同任务只有在输入不可变、输出根独立、服务与权威写入互不冲突、CPU/内存资源足够时
才并行。测试原始 Popen/wait、退出记录、矩阵身份和科研分母仍须完整保留。
共享读取或缓存必须有明确只读范围、完整哈希绑定和变化检测，不能依赖文件名、mtime
或过去一轮的 PASS。跨进程、跨部署或可写根不自动继承缓存。

已完成的最长 execution-final_report 窗口原始时间跨度约 73.96 分钟；完整安装等
扫描一次约 14.32 秒。因此没有证据表明安装哈希缓存能解决主要成本，不取消 fresh
bootstrap 的核验。当前冻结矩阵采用最多两个独立 case 并行；CPU、可用内存和每 case 输出
空间需持续测量，单 case 的 crash、recovery-1、recovery-2 顺序保持，任一失败停止
新增调度并等待已运行子进程留下实际退出，不省略失败或未运行分母。

当前第 32 轮完整安装 CI 的实际观测是 1795 个测试通过，耗时 7779.43 秒，完整
171 个源码文件覆盖 85.40%。这说明完整 CI 本身已有显著成本；开发局部修改先做
针对性验证，稳定后再执行冻结验收。该观测只属于 C32 的原始 CI，不授予 MVP 资格。

原生 verifier 的 CLI 在完整 `verify_bundle()` 后再次执行来源与场景核验。本轮管理
入口通过已冻结安装的公共 `verify_bundle()` 完整核验一次，
再检查已验证结果的 canonical bytes、schema 与 manifest hash。外层源代码加载检查、
只读挂载、原始 authority/bundle 前后库存和实际退出证据必须全部保留。局部入口测试
通过不能替代原生核验；采用时必须冻结新管理脚本及实际 argv 的哈希。

旧第31轮完整导出原始prelaunch至actual exit跨度约3小时3分钟，导出的saved
verifier-result也在这一跨度末尾生成；这是包含复制、来源与门核验的观测跨度，不能
冒充纯CPU或单个门耗时。其后原生核验在7200秒达到上限，保留实际wait-9和原件
库存未变记录。因此不能断言去掉重复CLI即可在两小时内完成。后继新管理脚本准备
14400秒原生上限和14700秒外层上限，其管理脚本已另行冻结、独立开发审查并启动等待；业务服务预算、来源谓词、
原生只读范围及PIT门不变，仍需原始wait和完整机械结果，不能延长已失败尝试。

本轮另设每60秒只读监测，观察已知服务及子进程的公开CPU、RSS、I/O和cgroup
OOM计数。进程采样会漏掉已经退出的子进程；服务累计CPU与存活进程CPU不能
互换。I/O会计和MemoryPeak不可用时明确标为unavailable，不能以RSS或当前
MemoryCurrent代替物理峰值，也不能把rchar当作原始科学数据的读取字节数。

真实交接前的管理证据检查同样必须使用已有专用ManagerExport读取器；先按普通
16MiB上限读取、随后才进行32MiB专用类型校验，仍会误拒合法大型索引。新的管理
入口只允许canonical、hash命名且绑定长度和部署的ManagerExport走专用读取器，
普通证据仍保持4MiB已知值扫描上限。局部合成容量测试不会运行真实交接或授予资格。

还须提前检查后续消费点：停止服务后的源导出会复制全部管理证据，完整bundle导出
也会再次读取它们。大型ManagerExport须保留原字节、完整文件清单和来源映射，并
单独按typed索引验证，不能列入普通case JSON路径。仅修正最初发布或真实交接前
的检查入口不足以解决整条链路的容量问题。

## 稳定后完整冻结

冻结实施提交与 wheel，再完整执行 CI、106 个场景、七门离线导出和独立原生核验。
每个结果来自该部署的原始采集与机械谓词；旧提交的 CI 或场景结果不自动资格化新提交。
若需要修正实现，产生新身份，按影响范围重新验收，保留失败与被替代的原件。

提前准备真实交接授权说明，列出实际传输的获准上下文范围、冻结研究模型与 CLI 调用
上限、不可观察的内部重试/token/费用，以及认证读取方式。实际离线就绪及公开预览
完成后才绑定其哈希，材料不得预填未来证据或用户批准。

真实交接仍须用户明确授权 authenticated model handoff 与 provider context transmission。
完成真实来源、保存响应 replay、独立根重执行及其余机械门之后，提交独立 HM-09 审查，
然后由 HM-10 整理用户文档、HM-11 登记接受范围。开发性能优化不扩大权限、研究家族
或资格声明，FR-03 和 P14 历史状态继续保留。
